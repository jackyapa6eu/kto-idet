# Проект: ОПГ Здоровья — Telegram-бот с мини-приложением

## Контекст
Есть Telegram-канал "ОПГ Здоровья" (Организованная Пляжная Группа здоровья) —
участники договариваются о совместных играх/тренировках по пляжному волейболу.

## Глобальная цель
Telegram-бот с мини-приложением (Mini App), где можно:
- создавать события (игра/тренировка: дата, время, место, макс. число участников и т.п.)
- записываться на события / отменять запись
- бот уведомляет записавшихся о статусе события (новое событие, изменения, напоминания)

## Стек

Схема: `backend/src/db/schema.ts` (таблицы `users`, `login_sessions`, `events`, `participants`, `event_reminders`). - **Авторизация:**
  - Внутри мини-аппа — Telegram-идентификация через `initData` (проверяется на бэкенде HMAC-подписью с `TELEGRAM_BOT_TOKEN`, см. `backend/src/telegramAuth.ts`). При каждом заходе апсертится строка в `users` (имя/аватар обновляются, см. `backend/src/users.ts`).
  - Вне мини-аппа (обычный браузер) — вход через **редирект в бота** (`frontend/src/components/TelegramBotLoginButton.tsx`), без номера телефона и SMS вообще: фронт создаёт одноразовую сессию (`POST /api/auth/session` → таблица `login_sessions`), открывает пользователю `t.me/<bot>?start=login-<token>`, пользователь жмёт Start в уже залогиненном Telegram-приложении, бот (`backend/src/bot.ts`, обработчик `/start`) подтверждает сессию его telegramId, а фронт всё это время поллит `GET /api/auth/session/:token` (раз в 2 сек, TTL сессии — 10 минут). После подтверждения бэкенд выдаёт JWT (30 дней, `hono/jwt`, секрет — `JWT_SECRET`) и удаляет сессию (одноразовая). Фронт хранит JWT в `localStorage`, шлёт `Authorization: Bearer <jwt>` (см. `frontend/src/api.ts`).
  - Ранее пробовали Telegram Login Widget — отказались: он не переиспользует существующую Telegram-сессию браузера и всё равно требует ввести номер телефона на экране `oauth.telegram.org` (там нет QR-входа). Редирект в бота полностью решает исходную проблему (SMS не доходит в регионе пользователя), т.к. использует уже залогиненное мобильное приложение.
  - Все защищённые ручки (`POST /api/events`, `GET /api/auth/me`) принимают либо `X-Telegram-Init-Data`, либо `Authorization: Bearer` — `createdByTelegramId` всегда берётся из проверенных данных, клиент не может его подделать.
  - На Vercel (backend) нужен env var `JWT_SECRET` (уже добавлен в Production).
  - Авторизация по номеру телефона (SMS) как отдельный механизм **отменена** в пользу входа через бота.

## Заметки / решения
- Frontend и backend — сознательно раздельные проекты (не Next.js монолит), чтобы попрактиковаться с Node.js отдельно.
- Backend-фреймворк — Hono (выбран осознанно ради практики с актуальной либой).
- Сеть в dev-окружении может быть нестабильной/медленной (npm install иногда занимает минуты) — не повод считать команды сломанными, просто ждать/повторить.
- В шаблоне Hono была прибита версия `typescript@^7.0.2` (текущий latest) — она падала при сборке именно на билд-машине Vercel (`Cannot read properties of undefined (reading 'readFile')`), локально проблему было не видно. Понизили до стабильной `5.9.3`. Если снова столкнёмся с непонятными крашами сборки только на Vercel — сначала проверять версию TypeScript.
- Бот и БД используют один и тот же токен/креды — хранятся только в Vercel env vars (production) и локальном `.env.local` (гитигнорится), в репозиторий не попадают.
- `getBotUsername()` в `backend/src/bot.ts` — статичное значение (env `TELEGRAM_BOT_USERNAME` с дефолтом `zdorovya_opg_bot`), не живой вызов `getMe()`: username бота практически не меняется, а сама ссылка `t.me/...` и так публична, так что нет смысла держать рантайм-зависимость от Telegram API на пути логина.
- Локальный `TELEGRAM_BOT_TOKEN` в `.env.local` на момент 2026-07-31 не проходит `getMe()` (404 Not Found) — то есть невалиден для реальных вызовов Telegram API (вебхук/бот локально не запустится). При этом HMAC-проверка `initData` продолжает "работать" локально, потому что тестовые данные для неё же и подписывались этим токеном — это не доказательство валидности токена. Прод, судя по всему, использует другой (рабочий) токен в Vercel env vars. Если понадобится тестировать бота локально — сначала проверить токен через `curl https://api.telegram.org/bot<TOKEN>/getMe`.
- **Напоминания о событиях** (`backend/src/reminders.ts`, `sendDueReminders`): шлются в чат за 30–90 минут до начала (окно, не точка) — за это отвечает внешний крон **cron-job.org** (не Vercel Cron: на Hobby-плане нет нужной частоты), который раз в 30 минут дёргает `POST /api/cron/reminders` с `Authorization: Bearer $CRON_SECRET`. Идемпотентность обеспечивает таблица `event_reminders` (один реминдер на событие, `onConflictDoNothing`). Окно шире шага крона специально — чтобы пропуск одного прогона крона не давал событию проскочить без напоминания.
- **Инцидент 2026-08-21/22 — Neon compute quota exceeded (500 на всех ручках с БД):** причина — крон дёргал `/api/cron/reminders` **раз в минуту**, а у compute стоит фиксированный `Scale to zero: 5 минут` (Launch-план это значение не даёт уменьшить, только вкл/выкл) — значит compute вообще не успевал засыпать и работал 24/7 (~180 CU-час/мес против бесплатных 100/мес). cron-job.org сам отключил джобу после 26 неудачных попыток. Фикс: интервал крона поднят до 30 минут + окно в `reminders.ts` расширено до 30–90 мин (см. выше), чтобы не терять напоминания при редком опросе. Для немедленной разблокировки апгрейднули Neon с Free на **Launch** (usage-based: $0.106/CU-час компьюта, $0.35/ГБ-мес storage; управляется через Vercel → Integrations → Neon → Settings → "Change Plan", там же способ оплаты). Тарификация Launch считается от даты апгрейда (22.08), а не задним числом с начала месяца. **План вернуть Free после 2026-09-01**: месячный счётчик CU-часов у проекта в Neon Console привязан к календарному месяцу и не обнуляется при смене плана — переключаться на Free раньше 1-го числа нельзя, тут же снова упрёшься в лимит и получишь паузу проекта. В Neon (Billing → Spending notifications) включены алерты на $16/$20 расхода в месяц как ранний сигнал, если потребление снова вырастет. **2026-09-07: план переключён обратно на Free** (Vercel → Integrations → Neon → Settings → Change Plan) — итоговый расход на Launch составил $1,20 (счёт за 8/22–9/1, 11.295 CU-час) + $0,80 за 1–7 сентября до переключения. Free-тир: 100 CU-час/проект, 0.5 ГБ storage/проект, без карты. Раз крон уже на 30-минутном интервале (см. выше), compute должен успевать засыпать (scale to zero: 5 мин) — если квота Free снова начнёт исчерпываться, проверять в первую очередь частоту крона/реальный трафик, а не сразу апгрейдить план.
