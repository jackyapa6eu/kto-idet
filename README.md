# Кто идёт

Telegram-бот с мини-приложением для организации сборов в чате
(тренировки, игры, квизы и т.п.): создание событий, запись/отмена,
напоминания, отметки оплаты. Бот — [@kto_idet_bot](https://t.me/kto_idet_bot).
Подробности стека и текущего статуса инфраструктуры — в `CLAUDE.md`.

Это форк [`obhg`](../obhg) (проект "ОПГ Здоровья") от 2026-09-07 — тот
был однотенантным ботом под один конкретный чат, `kto-idet` — попытка
превратить ту же идею в продукт, которым может пользоваться любой админ
группы для своей аудитории. Оригинал не трогаем, он живёт отдельно.

- `backend/` — Hono API + Telegram-бот (grammY) + Neon Postgres (Drizzle)
- `frontend/` — Mini App (React + TS + Vite + AntD + MobX)

## Функционал

**Мероприятия:**
- Создание/редактирование/удаление: название, место, дата и время (нельзя
  выбрать прошедшее — блокируется и в календаре, и в тайм-пикере, дата и
  время проверяются вместе), необязательная продолжительность (часы +
  минуты), лимит участников, тренер, стоимость, корт, реквизиты для
  перевода (номер/банк), комментарий.
- Запись/отмена записи участником; резерв, если мест не осталось
  (автоматически поднимается в основной состав при освобождении места).
  Организатор — тоже участник своего мероприятия по умолчанию и может
  выйти и вернуться обратно так же, как любой другой.
- Отметка «оплачено» 💰 и исключение участника («не придёт») — доступны
  только организатору.
- Повторяющиеся мероприятия («каждую неделю», платная фича) — следующее
  звено цепочки создаётся автоматически кроном, когда предыдущее уже
  наступило; остановить повтор — снять галочку при редактировании любого
  звена цепочки.
- Шаблоны мероприятий (на бесплатном тарифе — один «на пробу», на платном
  без ограничений) — быстрое повторное создание с теми же полями.
- Поделиться прямой ссылкой на мероприятие — открывает мини-апп сразу на
  нём, для любого участника Telegram-чата.

**Мини-апп:**
- Список мероприятий: прошедшие — полупрозрачные; идущие прямо сейчас
  (когда известна продолжительность) — подсвечены зелёным по токенам темы
  (корректно и в тёмной теме Telegram).
- Настройки организации: название в мини-аппе, оповещения вкл/выкл, могут
  ли участники сами создавать мероприятия (по умолчанию — только админы
  чата).
- Личный дашборд владельца бота (открывается deep-link'ом
  `?startapp=admin-0`, без кнопки в общем UI): статистика по всем
  подключённым чатам (сколько активны/в настройке/отключены/на удалении),
  лента последних мероприятий по всем чатам для модерации (удаление), и
  редактирование даты, до которой у организации оплачен платный тариф —
  единственный способ выдать/снять платный доступ, доступно только
  владельцу бота (`ADMIN_TELEGRAM_ID`).

**Бот и онбординг:**
- Мультитенантность — любой админ Telegram-группы сам подключает бота к
  своему чату, без нашего участия.
- Пошаговый визард настройки в личке (сделать бота админом →
  `/set_digest_here` → `/set_reminders_here` или пропустить), с кнопкой
  «🔄 Проверить» на случай, если апдейт от Telegram не пришёл или не
  обработался вовремя.
- Закреплённая сводка предстоящих мероприятий в топике — редактируется на
  месте при любом изменении, плюс раз в сутки принудительно пересобирается
  кроном, чтобы вчерашние мероприятия не залёживались там без активности в
  чате.
- Анонс о новом мероприятии в топике напоминаний, редактируется на месте
  при изменении события.
- Напоминание за 30–90 минут до начала с тегом записавшихся (резерв не
  тегается).
- Восстановимое удаление: если бота выгнали из группы — 14 дней на
  возврат без потери данных, затем безвозвратное удаление кроном.
- Меню в личке для тех, кто администрирует несколько групп сразу.

**Авторизация:**
- Внутри мини-аппа — через `initData` Telegram, без дополнительных шагов.
- Вне мини-аппа (обычный браузер) — вход через редирект в бота, без
  номера телефона и SMS, JWT на 30 дней.

## Roadmap: продажа тренерам/организаторам (SaaS)

Статус: инфраструктура развёрнута 2026-09-07, мультитенантность (этапы
1–4 и 6 ниже) реализована и работает в проде — см. «Функционал» выше и
пошаговый план ниже. Открыто: блокировка организации из админки (этап 5)
и биллинг/самостоятельная оплата (этап 7) — сейчас платный статус
организации выставляется вручную владельцем бота через дашборд (см.
«Функционал» выше), самостоятельной оплаты пока нет.

### Требования к продукту

- **Простое развёртывание тренером** — без ручной помощи от нас на каждую
  продажу (тренер сам подключает бота к своей группе).
- **Централизованная видимость и контроль** — мы должны видеть все
  активные "развёртывания"/организации в одном месте и иметь возможность
  заблокировать любое (неоплата, злоупотребление и т.п.).
- **Настройки на тренера**:
  - название группы/организации;
  - включить/выключить оповещения (сводка в топике, напоминания);
  - разрешить/запретить "ученикам" самим создавать мероприятия (сейчас
    может любой участник группы — нужно сделать переключаемым правом
    организатора).

### Рыночное исследование (2026-09-07)

Смотрели на аналоги — Telegram-боты и соседние продукты (фитнес-CRM,
командные приложения) для записи на тренировки/игры — их цены и модели
монетизации.

**Главная находка — прямой бесплатный конкурент уже существует, и это
проверено напрямую на сайте (2026-09-07):** [Games от
FindSport](https://games.findsport.ru/) делает практически то же самое
(создание игры с датой/местом, запись в клик, кто оплатил/нет,
автонапоминания). На сайте прямо написано «Бесплатно», в FAQ — «Это
бесплатно? Да», а в публичной оферте findsport.ru отдельно закреплено, что
комиссию с организаторов/участников они не берут. Монетизируются они,
судя по всему, на стороне площадок/венues (что не раскрыто публично), а
не на организаторе игры. Конкурировать с этим "в лоб" на голом
функционале записи — проигрышная стратегия.

**Цены и модели в соседних нишах:**

| Продукт | Модель | Цена |
|---|---|---|
| Gymboss / «Бот Фитнес Центр» (телеграм-фитнес) | Подписка после триала | 190–890 ₽/мес |
| Contez (запись в фитнес-клубы + оплата в боте) | По числу активных подписчиков бота | не публикуют цифры |
| Teamer (команды, RSVP) | Бесплатное ядро + комиссия с платежей | 2.9% + 20p за транзакцию (была премиум-подписка ~€4.95/мес) |
| Centro (клубы) | Плоская подписка | $25/мес |
| InviteMember (Telegram-подписки) | По объёму продаж, не по числу подписчиков | от $19/мес |
| Spond, Heja (команды) | Бесплатно | — |

**Наблюдаемые паттерны монетизации:** (1) freemium с лимитом по числу
участников/подписчиков или по объёму продаж — самый частый вариант именно
для Telegram-продуктов; (2) комиссия с платежей вместо подписки — там, где
ключевая фича — сбор денег с участников; (3) плоская месячная подписка
организатору — типична для готовых "клубных" B2B-продуктов; (4) заметная
доля прямых конкурентов в этой нише вообще бесплатна (FindSport, Spond,
Heja).

**Вывод и как это меняет план:** комиссия с платежей (модель Teamer)
**не подходит** — деньги за тренировки идут напрямую тренеру обычным
переводом на карту/телефон (см. поля `paymentPhone`/`bank` в событии),
через бот не проходят ни рубля, брать комиссию не с чего технически, пока
в продукте нет собственного платёжного приёма. Значит, реалистичный
вариант — **подписка организатору** (плоская, как у Centro/фитнес-ботов,
или freemium с лимитом на число участников/активных событий, как у
Contez/InviteMember). Платить будут не за саму запись на игру (она уже
есть бесплатно у FindSport), а за то, чего у бесплатных аналогов нет:
встроенность в уже существующий чат тренера (а не отдельная
платформа-агрегатор), гибкая настройка под конкретную группу (см. раздел
настроек ниже) и удобный трекинг "кто оплатил" (💰) — как учётный
инструмент для тренера, а не как платёжный шлюз. Если в будущем добавить
реальный приём оплаты через бота (например, Telegram Payments) —
комиссионную модель можно будет пересмотреть, но это отдельная фича, не
предпосылка для текущего плана.

**Отклонённый вариант — реклама в мини-аппе:** проверили экономику
(2026-09-07) — специализированные рекламные сети для Telegram Mini Apps
(в первую очередь Adsgram) заявляют CPM $3.8–$16 за 1000 показов, но
реальные кейсы с такими цифрами — это crypto tap-to-earn кликеры с
многократными открытиями в день, а не утилита для записи на сборы. При
низкочастотном использовании (люди заходят раз в несколько дней
записаться/посмотреть событие) прикидка для 500–2000 участников —
буквально **$4–130/мес**, скорее у нижней границы. Это меньше, чем
подписка даже одного платящего тренера, а баннеры в инструменте, за
который и так планируем брать деньги, портят доверие. **Рекламу в план
монетизации не закладываем.**

### Ключевое архитектурное решение

Один общий бот на всех тренеров, тенант = Telegram-чат (`chat_id`), а не
бот на каждого тренера отдельно — это ближе к уже существующей модели
(digest/reminders и так привязаны к chat_id/thread_id) и не плодит ручной
сетап нового бота/деплоя при каждой продаже.

Централизованная видимость/блокировка тогда реализуется не как "видеть
серверы", а как **админ-реестр организаций** (таблица `organizations` +
админский экран/эндпоинт), где у каждой записи есть статус
(активна/заблокирована) — блокировка это флаг в БД, а не отключение
инфраструктуры.

### Черновой план по этапам

1. **Форк инфраструктуры — готово (2026-09-07):** GitHub-репозиторий
   (`jackyapa6eu/kto-idet`), бот `@kto_idet_bot` (BotFather, токен в Vercel
   env, вебхук зарегистрирован), Vercel-проекты `kto-idet-backend`/
   `kto-idet-frontend` (задеплоены в прод), Neon-проект `kto-idet-db`
   (Free-тир). Смоук-тест инфраструктуры (бэкенд отвечает, `getWebhookInfo`
   без ошибок) пройден; end-to-end сценарий в реальном чате — ещё нет, см.
   чек-лист в `CLAUDE.md`.
2. **Модель данных под мультитенантность**:
   - таблица `organizations`: id, название, `telegramChatId`,
     `digestThreadId`, `reminderThreadId`, `ownerTelegramId`, флаги
     настроек (оповещения вкл/выкл, кто может создавать события), статус
     (активна/заблокирована).
   - `organizationId` (FK) в `events`; сводка стала per-org через
     `organizations.digestChatId/digestThreadId/digestMessageId` (сделано
     2026-09-07) — старая таблица-синглтон `channelDigest` больше не
     используется в коде (саму таблицу из БД не убирали, но она мертва).
     `eventReminders` per-event уже и так была (`eventId` → `events.organizationId`
     даёт организацию транзитивно), схема не менялась; сама рассылка
     кроном (`reminders.ts`) пока не переведена с env на `organizations` —
     см. открытый пункт в `CLAUDE.md`.
   - `users`/`participants`/JWT-логин остаются глобальными — один
     Telegram-пользователь может состоять в нескольких группах разных
     тренеров.
3. **Онбординг тренера без нашего участия** — детальный флоу (продумано
   2026-09-07, исходит из ограничения Telegram: бот не может получить
   список топиков форума через API, а мини-апп не знает, из какого
   чата/топика её открыли, если это не передано явно — значит, надёжно
   привязать место может только сама команда, отправленная тренером прямо
   в нужном топике, откуда `chat_id`+`message_thread_id` считываются из
   входящего сообщения):
   1. Тренер находит бота сам (по короткому описанию профиля в Telegram —
      `setMyDescription`/`setMyShortDescription`, текст должен явно вести
      к нажатию Start) и жмёт **Start в личке**. Это и есть точка входа:
      никакой группы ещё нет, поэтому объяснять что-либо про конкретную
      группу рано — бот просто рассказывает общий рецепт подключения
      (добавить в группу, выдать права администратора, выполнить
      `/set_digest_here` в топике для сводки и `/set_reminders_here` в
      топике для оповещений, можно один и тот же топик для обоих). Раз
      тренер сам инициировал приватный чат, дальше боту не мешает
      ограничение Telegram "нельзя первым написать в личку" — оно
      актуально только для случаев ниже, где ещё никто не жал Start.
      Это — для тех, кто ещё не администрирует ни одной группы; если уже
      администрирует хотя бы одну, плейн `/start` вместо этого текста
      сразу показывает **меню** (см. п.6 ниже) — инструкция по
      подключению им уже не актуальна, а быстрый доступ к своим группам
      актуальнее.
   2. Тренер добавляет бота в группу админом. Событие `my_chat_member`
      даёт и `chat.id`, и `from.id` (кто добавил) — этого достаточно,
      чтобы сразу создать черновую `organizations` (status =
      `setup_pending`, `ownerTelegramId` = добавивший, `telegramChatId` =
      группа, `name` = название группы по умолчанию) без единого действия
      тренера. Полную инструкцию (те же шаги, что и в п.1, но уже с
      названием конкретной группы) бот шлёт добавившему **в личку** — раз
      он только что нашёл бота через профиль и жал Start (п.1), личка уже
      открыта. Если отправка в личку всё же не удалась (бота добавили без
      этого шага — переслали, добавили через "похожие боты" и т.п.) —
      запасной вариант: короткое предупреждение прямо в группе с просьбой
      сначала нажать Start в чате с ботом.
   3. `/set_digest_here` — сохраняет `digestChatId`/`digestThreadId` из
      контекста входящего сообщения. В группе эта команда **никогда не
      отвечает в чат** — только в личку вызвавшему, и само сообщение с
      командой удаляет после обработки (`finally`, независимо от исхода) —
      топик не должен видеть ничего служебного. Сначала проверяет права
      **вызвавшего** (`ownerTelegramId` или админ чата через
      `getChatMember`) — команда предназначена только для администраторов
      группы; если прав нет — отказ уходит в личку, а не в группу. Затем
      проверяет права **самого бота** в этой группе — если бота ещё не
      сделали администратором, команда молча ничего не меняет (не сохраняет
      топик) и пишет об этом владельцу в личку. Дальше бот старается вообще
      не оставлять в топике ничего лишнего: шлёт сразу боевую сводку
      (`buildDigestText()`, а не тестовую заглушку) — это и есть то
      сообщение, которое дальше будет редактироваться на месте при каждом
      изменении событий (`digestMessageId` сохраняется в `organizations`
      для будущего редактирования), закрепляет его, и сам удаляет служебное
      "Х закрепил(а) сообщение" (единый хендлер на `message:pinned_message`,
      чистит это в обеих командах). Если не хватает конкретно права
      "закреплять сообщения" — тоже в личку вызвавшему. По завершении —
      снова личка: "готово", плюс рекомендация закрыть топик от новых
      сообщений (только если это действительно топик форума), чтобы
      участники не заваливали сводку своими сообщениями, а бот продолжал её
      редактировать даже в закрытом топике. `/set_reminders_here` —
      аналогично для `reminderChatId`/`reminderThreadId` (без сводки —
      просто тестовое сообщение-метка), с той же логикой "ничего в чат,
      всё в личку, команда удаляется"; если не вызвана отдельно —
      `/set_digest_here` по умолчанию проставляет то же место и для
      напоминаний, чтобы не блокировать настройку на полпути. Первая
      успешная привязка переводит org из `setup_pending` в `active`.
      Переезд в другой топик — просто повторный вызов той же команды в
      новом месте, отдельной команды "отвязать" не нужно.
   4. Мини-апп: сделано. Кнопка «Открыть / Записаться» в сводке несёт
      `?startapp=org-<id>` — по нему фронт понимает, для какой организации
      показывать список (`GET /api/events?organizationId=<id>`,
      `POST /api/events` с `organizationId` в теле). Бэкенд проверяет по
      каждому запросу: организация существует и `active`, вызывающий
      реально состоит в её Telegram-чате (`isChatMember`, per-org замена
      старого глобального `requireGroupMember`/`GROUP_CHAT_ID` из env) —
      однотенантный код полностью убран. `membersCanCreateEvents` из
      `organizations` тоже уже учитывается при создании события. Открытие
      мероприятия по прямой ссылке (`event-<id>`) не требует членства в
      группе на уровне самого запроса (`GET /api/events/:id` доступен всем,
      как и в однотенантной версии) — но список группы под модалкой всё
      равно показывается, если вызывающий состоит в её чате: ссылка не
      несёт `organizationId` явно, поэтому фронт достаёт его из ответа
      `GET /api/events/:id` (там уже есть `organizationId` мероприятия) и
      только после этого запрашивает `GET /api/events?organizationId=...`
      — на время этого шага под модалкой крутится спиннер. Без контекста
      вообще (ни `org-`, ни `event-` в
      `start_param`) — это уже холодный визит (постоянная кнопка меню бота,
      прямая ссылка на мини-апп без параметров), а не переход из чата:
      вместо попытки сразу авторизовать показывается `Landing` — статичная
      страница о боте с кнопкой «Добавить бота в свой чат»
      (`frontend/src/components/Landing.tsx`).
   5. Граничные случаи — сделано 2026-09-08, два разных исхода `my_chat_member`,
      не один общий `disconnected`, как думали изначально. Бота **разжаловали
      из админов, но он ещё в группе** — это обратимо без потери данных
      (события/сводка никуда не делись), просто помечаем org `disconnected`
      и обновляем визард в личке владельца. Бота **выгнали из группы
      целиком/он вышел** — `status = 'removed'` + **soft delete на 14 дней**
      (`scheduleOrganizationDeletion`, `scheduledDeletionAt = now() + 14d`):
      сами события и настройки пока не трогаем, только предупреждаем владельца
      в личке (в его же визард-сообщении) с датой, до которой можно всё
      восстановить. Если за это время бота добавят обратно —
      `createOrganizationDraft` сбрасывает таймер и возвращает `active` без
      повторной настройки (данные же никуда не делись). Если нет — отдельный
      крон-эндпоинт `POST /api/cron/purge-organizations` (тот же `CRON_SECRET`,
      что и `/api/cron/reminders`, но частота нужна гораздо реже — раз в сутки
      достаточно) находит все `removed`-организации с истёкшим сроком и стирает
      насовсем: события (каскадом их участников и `eventReminders`), затем саму
      запись `organizations` — оба крона (`reminders` каждые 30 минут,
      `purge-organizations` раз в сутки) настроены на cron-job.org 2026-09-08,
      см. чек-лист в `CLAUDE.md`. Команды
      `/set_..._here`, вызванные в личке с ботом, — отклоняются с
      объяснением; уже известный по текущему коду риск (см. комментарий в
      `digest.ts`) — если топик закрыт для новых сообщений и одновременно
      кто-то вручную удалил закреплённое сообщение сводки, бот не сможет
      прислать новое, пока топик не откроют.
   6. **Меню в личке** — сделано 2026-09-08: один человек вполне может
      администрировать сразу несколько групп (тренер с двумя секциями,
      совладелец чужой группы и т.п.), поэтому плейн `/start` не может
      просто вести в одну-единственную "текущую" группу. Вместо этого
      бот держит в личке **ровно одно активное меню**:
      `getManagedOrganizations` находит все `organizations`, где
      пользователь владелец или админ чата (`isChatAdmin` по каждой —
      без лишних вызовов к Telegram для тех, где он и так `ownerTelegramId`);
      если группа одна — сразу открывается её карточка (кнопка «⚙️ Открыть
      настройки», ведёт на `?startapp=settings-<id>`), если несколько —
      список для выбора, а из карточки конкретной группы «⬅️ Назад»
      возвращает к списку. Навигация внутри визарда (callback_query
      `menu:root`/`menu:org:<id>`/`menu:skip_reminders:<id>`, прогресс от
      `my_chat_member`/`/set_..._here`) правит одно и то же сообщение через
      `editMessageText` (`showMenu` в `bot.ts`) — новых не шлёт. Но именно
      `/start` — исключение и всегда пересоздаёт сообщение с нуля
      (`restartMenu`: удаляет прошлое, шлёт новое), а не редактирует: правка
      от `editMessageText` не создаёт уведомления и не поднимает сообщение
      наверх чата (ограничение платформы), из-за чего 2026-09-08 реальное
      обновление визарда выглядело как "бот молчит" — сообщение обновлялось,
      но было незаметно погребено в истории. `/start` — явное действие
      пользователя, поэтому там важнее гарантированно видимое новое
      сообщение, чем формальное "одно сообщение навсегда". Для той же
      защиты `sendFreshMenu` дополнительно закрепляет (`pinChatMessage`)
      сообщение баннером наверху личного чата при каждой новой отправке.
      id сообщения хранится в `users.lastMenuMessageId`. Организации не в
      статусе `active` помечаются ⚠️ и в списке, и в карточке (текстом —
      "настройка не завершена"/"бот отключён от группы"/"группа
      заблокирована"), а не просто пропадают из вида.
4. **Настройки организации** — сделано 2026-09-08 (мини-апп,
   `frontend/src/components/OrgSettingsForm.tsx` + `backend` роуты
   `GET`/`PATCH /api/organizations/:id`). Доступ — владелец или админ чата
   (`isChatAdmin`, та же проверка, что у `/set_..._here`), не только
   буквальный `ownerTelegramId`. Вход: кнопка «⚙️ Настройки» в шапке
   мини-аппа (видна только тем, кому доступно), либо deep-link
   `?startapp=settings-<id>` — им бот сопровождает личку "Готово!" после
   **первой** настройки `/set_digest_here`/`/set_reminders_here` (не при
   каждом повторном вызове), заодно явно объясняя новый дефолт (см. ниже).
   Что внутри:
   - название — **только для мини-аппа** (2026-09-08): в кнопках/сообщениях
     самого бота (список групп, шаги визарда, ошибки) везде используется
     живое `getChat(telegramChatId).title` из Telegram, а не это поле —
     чтобы бот не расходился с реальным названием чата, если его в
     мини-аппе переименовали во что-то своё. `organizations.name` при этом
     остаётся источником для фолбэка, если бот уже потерял доступ к чату
     (removed/disconnected) и живое название получить не может;
   - переключатель "оповещения включены" — реально управляет и
     `syncChannelDigest`, и `sendEventCreatedNotification`/
     `updateEventNotification` (при выключении бот тихо ничего не шлёт и
     не редактирует, `digestMessageId`/сводка остаются как есть);
   - переключатель "участники могут создавать мероприятия" — **по
     умолчанию выключен** (изменили дефолт со старого "могут все": слишком
     похоже на спам от случайных участников); пока выключен — создавать
     может владелец или любой админ чата. `POST /api/events` и фронт
     (кнопка "Создать" в `EventsList`) читают один и тот же флаг
     `canCreateEvents` из `GET /api/organizations/:id` — участникам без
     прав вместо кнопки показывается объяснение, а не спрятанная ошибка
     после попытки.
   - привязки топиков (сводка/оповещения) в этот экран не выносили — их
     показ/перенос остаётся через `/set_..._here` (см. п.3), отдельный
     read-only блок в настройках не делали за ненадобностью.
5. **Админ-реестр** (для нас, не для тренеров) — частично сделано:
   дашборд (`AdminDashboard.tsx`, открывается `?startapp=admin-0`)

6. **Пилот** — вручную завести 1-2 организации для знакомых тренеров

7. **Биллинг и лимиты** — отдельный этап после того, как техническая

### Лендинг и SEO — сделано 2026-09-08

`Landing.tsx` (тот самый экран для холодного визита без organizationId, см.
раздел про мультитенантный мини-апп выше) переписан на чистый HTML/CSS без
antd (`Landing.css`) — не ради производительности, а чтобы его можно было
безопасно отрендерить в Node-скрипте: antd в SSR-контексте — источник
лишних рисков (стили через CSS-in-JS, потенциальные побочные эффекты при
импорте), а лендингу для рендера ничего из этого не нужно. Контент
расширен под SEO-ключевые фразы (не 3 строки, как раньше) — что умеет,
как подключить, FAQ на нативных `<details>` (аккордеон без JS).

**Технический SEO:**
- `frontend/index.html` — `title`/`description`, Open Graph и Twitter
  card теги, `canonical` на `https://kto-idet.ru/`.
- `frontend/public/robots.txt` и `sitemap.xml` — статика, отдаётся как
  есть.
- **Главное — пререндер в статический HTML** (`frontend/scripts/prerender-landing.tsx`,
  запускается `tsx` после `vite build`, см. `npm run build`): рендерит
  `<Landing />` через `renderToStaticMarkup` и вшивает результат прямо в
  `dist/index.html` вместо пустого `<div id="root"></div>`. Причина —
  без этого весь контент виден краулеру только после выполнения JS-бандла;
  Google это худо-бедно умеет, а **Яндекс** (важно для домена `.ru`) — плохо,
  может вообще не проиндексировать текст. Пререндер — не полноценный SSR
  (рендер на каждый запрос не нужен, лендинг статичен и ни от чего не
  зависит), а SSG в одну сборку — не понадобился Next.js/другой фреймворк,
  архитектура не изменилась.
  - `import './Landing.css'` намеренно живёт не в `Landing.tsx`, а в
    `App.tsx` — Node/`tsx` не умеет резолвить CSS-импорты напрямую, а
    прогонять сборку через полноценный Vite ради одного файла не стали.
  - Сам скрипт использует `React.createElement` вместо JSX в своём теле
    (хотя `Landing.tsx` внутри — обычный JSX) — `tsx`/esbuild не подхватывает
    `"jsx": "react-jsx"` из `tsconfig.app.json` для файлов вне `src/` через
    directory-based резолюцию; собрано через явный `tsx --tsconfig tsconfig.app.json`,
    но и этого хватило только для файлов, которые сам React импортирует, не
    для JSX прямо в точке входа.
  - React на клиенте всё равно полностью перерисовывает `#root` через
    `createRoot().render()` (не `hydrateRoot`) — расхождения в разметке
    между пререндером и клиентским рендером не страшны, это не hydration.
- **Не сделано:** регистрация в Google Search Console и Яндекс.Вебмастере
  (это разовые действия в вебе, привязанные к аккаунту — не код),
  `og:image` (нет готового баннера-картинки 1200×630), обратные ссылки/
  каталоги ботов — маркетинг, не разработка.
